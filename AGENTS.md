# Правила работы с topsbottg

## Репозиторий

- `src/topsbottg/` — бот, API, модели и worker.
- `frontend/` — Mini App без frontend-фреймворка.
- `migrations/versions/` — история Alembic.
- `tests/` — Python, PostgreSQL, JavaScript и браузерные тесты.
- `scripts/` — обслуживание и деплой; правила CI — в [docs/ci.md](docs/ci.md).

Перед правкой проверь актуальную ветку, состояние рабочего дерева и связанные вызовы. Не стирай незакоммиченные изменения.

## Изменения

- Для новых задач по умолчанию создавай отдельную feature-ветку от свежего `main`. Если пользователь явно просит коммит в `main`, выполняй именно это; не создавай PR вместо прямого коммита.
- Один PR — одна задача. Не добавляй посторонний рефакторинг.
- При изменении API обновляй вызывающий код и тесты. Для изменения схемы создавай новую миграцию, не меняй уже применённые.
- Сохраняй совместимость с ранее записанными данными, если задача не предусматривает миграцию или удаление.
- Приложение запускает Telegram polling и worker вместе: не поднимай второй экземпляр с тем же токеном.
- Не добавляй внешнюю очередь, фреймворк или сервис без необходимости.
- Не записывай в Git токены, пароли, закрытые ключи и персональные данные.

Комментарии оставляй только там, где без них неясна причина решения, ограничение или порядок блокировок. Не пересказывай код и не оставляй пометки об этапах PR, будущих планах или действиях ассистента.

Документация должна описывать существующую реализацию. Сверяй утверждения с Compose, настройками, API, workflow и тестами. Не представляй ожидаемое поведение как проверенное.

## Коммиты и PR

Пиши конкретные названия коммитов и PR. **Описание PR — короткий текст инженера для другого инженера**, а не отчёт ассистента. Два-три небольших абзаца по делу: что изменилось и, только если важно, какие последствия у миграции или ограничения совместимости. Не используй шаблонные заголовки «Что изменено», «Проверки», «Итог», длинные списки очевидных действий, фразы «в рамках данного PR», «реализована возможность», «обеспечена поддержка», «успешно протестировано». Не перечисляй инструменты и тестовые сценарии ради объёма. Названия коммитов — обычные короткие формулировки изменений, без канцелярита.

Отчёт о выполненной работе, статус CI, слова о merge/deploy и другую служебную информацию пиши пользователю отдельно, не в описание PR. Перед отправкой перечитай описание и вычеркни каждую фразу, которая не помогает ревьюеру понять изменение.

Не выполняй merge, force-push, удаление веток и операции с production без прямого поручения. **Push в `main` автоматически запускает CI и, при успехе, production deploy**; учитывай это перед прямым коммитом, включая изменения только документации.

## Проверки

Выбирай проверки по изменённым файлам. Типовые команды:

```bash
uv sync --locked --extra dev
uv run --locked ruff check .
uv run --locked python -m pytest -q -m "not postgres"
node --check frontend/app.js
node --test tests/js/*.test.mjs
git diff --check
```

Для frontend используй `npm ci`, `npm run test:browser` и реальные скриншоты. При изменении SQL-моделей или транзакций запускай тесты PostgreSQL; при добавлении миграции — `alembic upgrade head` на тестовой базе. В GitHub Actions все проверки выполняются выборочно по [docs/ci.md](docs/ci.md).

Если CI упал, разбирай лог и исправляй причину, а не отключай проверку. В отчёте пользователю отличай реально прошедшие проверки от непроведённых. Не объявляй CD успешным до завершения соответствующей задачи.
