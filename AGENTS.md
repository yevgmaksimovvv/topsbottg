# AGENTS.md

## Навигация

- `src/topsbottg/` – Python-приложение: Telegram-бот, API, бизнес-логика, модели и фоновые задачи.
- `frontend/` – интерфейс Mini App (HTML, CSS, JavaScript).
- `migrations/versions/` – миграции Alembic.
- `tests/` – автоматические тесты.
- `README.md`, `pyproject.toml`, `docker-compose.yml` – запуск, зависимости и конфигурация.

## Работа с Git и Pull Requests

- Перед началом проверь корень репозитория (`git rev-parse --show-toplevel`), текущую ветку и `git status`. Не теряй и не перезаписывай существующие изменения пользователя.
- Для новой задачи с изменениями кода работай в отдельной ветке `feature/<краткая-тема>` от актуального `main`. Если задача продолжает уже открытый PR, используй его ветку, не создавай дублирующий PR.
- Держи PR в рамках одной задачи. Не включай посторонние изменения и не переписывай чужие коммиты.
- После реализации и локальных проверок создай осмысленный commit, отправь **только рабочую feature-ветку** и создай либо обнови PR в `main`. Это разрешено для порученной задачи на реализацию, если пользователь прямо не ограничил публикацию. Не отправляй изменения напрямую в `main`.
- В описании PR кратко укажи цель, основные изменения, результаты проверок, миграции и существенные риски. Предоставь ссылку на PR.
- Проверь фактический результат GitHub Actions. Если CI упал, изучи причину, исправь её и обнови PR. Не отключай проверки и не ослабляй тесты ради зелёного статуса.
- Если нет доступа для push или создания PR, не имитируй успех: сохрани изменения локально и сообщи, что требуется сделать вручную.
- Без отдельного разрешения не выполняй merge, деплой, force-push, удаление веток, сброс или потерю изменений, изменение работающих сервисов и операции с production-данными.

## Изменения кода

- Изучай затронутые файлы и связанные вызовы; для локальной правки не нужен аудит всего репозитория.
- Решай задачу минимальными согласованными изменениями. Не добавляй несвязанный рефакторинг и зависимости без необходимости.
- Сохраняй существующие данные и корректную обработку ранее созданных записей. Не добавляй поддержку устаревших внутренних API-контрактов, если frontend и backend обновляются вместе и задача не требует иного.
- При изменении контракта обновляй все затронутые уровни, вызовы и тесты.
- Следуй соглашениям проекта. Не меняй стек без необходимости.
- Не скрывай ошибки пустыми `except`, подавлением проверок или фиктивными успешными результатами.
- Для изменения схемы БД создавай новую миграцию Alembic; не переписывай уже применённые. Проверяй миграции на PostgreSQL, когда меняется схема.
- Не раскрывай и не коммить токены, пароли, приватные ключи и реальные персональные данные.

## Проверка

- Добавляй регрессионные тесты для изменённого поведения. Не подгоняй тесты под ошибочную реализацию.
- Выполняй подходящие проверки; перед завершением по возможности запускай:

```bash
uv sync --locked --extra dev
uv run --locked python -m pytest -q
uv run --locked ruff check .
git diff --check
```

- Для изменённого JavaScript проверяй синтаксис через `node --check`; изменения интерфейса по возможности проверяй в браузере.
- Проверки миграций и Docker-сборки выполняй при затрагивающих их изменениях; CI в PR должен проходить полностью.
- Отличай выполненную проверку от недоступной. Не утверждай, что CI, браузер или production проверены, если это не так.

## Результат

- Отвечай по-русски, кратко: что изменено, какие проверки выполнены, что осталось непроверенным.
- Для задач с PR укажи ветку, ссылку на PR и фактический статус CI. Не называй PR готовым к merge до успешных проверок и ревью.
